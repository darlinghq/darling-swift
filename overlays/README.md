# Swift SDK overlays built from source

Swift.org toolchains stopped shipping the Darwin SDK overlays, so the copies in this repository were x86_64-only (Swift 5.2.2). The CMake build of this repository builds six of them from source, for every 64-bit slice the Darling build produces (the x86_64 and arm64 slices of `DARLING_ARCHS`), and installs them in place of the 5.2.2 ones. Four are built from the last open-source Swift sources; `os` and `XPC` were never open source, so they are written from Apple's public API documentation and the imported symbol names (no Apple code).

## Coverage of what macOS 26 apps import

Measured against every binary in `/System/Applications` of a macOS 26.6.2 install:

- **ObjectiveC:** 14/14 symbols.
- **CoreFoundation:** 15/15, including the `$s12CoreGraphics7CGFloatV…` metadata and conformances.
- **os:** 44/44.
- **XPC:** 21/21.
- **Dispatch:** 94/104 before `Schedulers+DispatchQueue.swift`; the missing 10 are the Combine `Scheduler` conformance of `DispatchQueue` and its `SchedulerTimeType`/`SchedulerOptions` types, which that file (`release/5.4`) now provides. `libswiftDispatch` links Combine weakly, as on macOS, so programs that do not use Combine do not need it.

## Building

The Foundation overlay also needs a checkout of apple/swift-foundation and of swiftlang/swift-cmark, both at the tag `swift-6.3.3-RELEASE` (`SWIFT_FOUNDATION_SOURCE_DIR`, `SWIFT_CMARK_SOURCE_DIR`; by default the sibling directories `../swift-foundation` and `../swift-cmark` of this repository, which the main repository provides as submodules). Configuring stops with a message when a checkout is missing. swift-cmark's C sources are compiled into libswiftFoundation with hidden visibility, so none of its symbols is exported.

`CMakeLists.txt` in the parent directory builds the overlays with the Swift toolchain that the main repository's `cmake/swift_toolchain.cmake` finds (`-DSWIFT_TOOLCHAIN=<root>` selects one, `-DSWIFT_TOOLCHAIN=OFF` skips them). Without a toolchain the overlays are skipped and the rest of the build is unaffected. The function `add_darling_swift_library` (main repository, `cmake/darling_swift.cmake`) compiles each overlay with `swiftc -frontend` for `<arch>-apple-macosx26.0` against Darling's source-tree SDK and the module interfaces in `stdlib-modules/`, and links it with Darling's ld64 against Darling's libSystem, libobjc and CoreFoundation. The overlays import each other, so the targets depend on one another in the order Darwin, ObjectiveC and CoreFoundation, Dispatch, then os and XPC.

The toolchain is the Linux Swift release matching `version.txt` (for example `swift-6.3.3-RELEASE-debian12.tar.gz` from download.swift.org); its `swiftc -frontend` cross-compiles to `apple-macosx`. The Darling SDK must contain the Clang module maps and API notes for Darwin, ObjectiveC, Dispatch, os, XPC and CoreFoundation, and the `sys/cdefs.h` default-platform fix. Without that fix, arm64 code links against `$UNIX2003` symbol variants that don't exist. The Dispatch overlay needs the libdispatch with the `OS_dispatch_queue_serial_executor` class.

## CoreData

`libswiftCoreData.dylib` is built from source for the architecture of the Darling build (it was a prebuilt x86_64-only binary of the Swift 5.2.2 release). It has `NSManagedObjectContext.fetch(_:)` and `count(for:)` for `NSFetchRequest<T>`, the `CocoaError.Code` values and static properties of CoreData, and the `NSFetchRequestResult` conformances of `NSNumber`, `NSDictionary`, `NSManagedObject` and `NSManagedObjectID`. `CoreData/CocoaError.swift` and `CoreData/CoreData.mm` are the files of the same names in `apple/swift` tag `swift-5.2.2-RELEASE`, `stdlib/public/Darwin/CoreData`, unmodified.

`CoreData/NSManagedObjectContext.swift` is adapted from the Swift project (`swiftlang/swift`, `stdlib/public/SDK/CoreData/NSManagedObjectContext.swift`, commit ba33f9e0b772015326bdecc0d597b2ac9fc61717). It keeps the public signature of `fetch(_:)` (generic over `NSFetchRequestResult`, throwing, returning a typed array) and the file header with the copyright and licence lines; the body is rewritten to call a small Objective-C shim (`shims/CoreDataOverlayShims.h`), and `count(for:)` is written the same way. The shim is needed because Swift imports `-executeFetchRequest:error:` and `-countForFetchRequest:error:` of Darling's CoreData with the same names and equivalent types as the generic methods, and a direct call resolves to the generic method itself (an endless recursion). Copyright: 2014 - 2017 Apple Inc. and the Swift project authors. Licence: Apache License v2.0 with Runtime Library Exception (https://swift.org/LICENSE.txt).

Not included: the CoreData additions of newer SDKs (`NSPersistentStore.StoreType` and the `addPersistentStore(type:...)` and `migrateStore(from:...)` methods, the non-generic `fetch(_:)` returning `[Any]`, the `ObservableObject` conformance and subscript of `NSManagedObject`, the staged-migration initializers and `NSManagedObject.fetchRequest()`). `tests/coredata_fetch.swift` (with `coredata_fetch_helper.m`, which makes the model, store and requests in Objective-C) covers the generic fetch and count, the NSError of a failing fetch, the CocoaError codes and the conformances.

## Tests

`tests/os_xpc.swift` covers `Logger`, `os_log` with arguments, signpost IDs and intervals, `OSAllocatedUnfairLock` across threads, `XPCDictionary`/`XPCArray` and `XPCSession`. `tests/objc_only.swift` and `tests/objc_cf.swift` cover an NSObject subclass with `@objc` methods and selectors, NSObject `Equatable`/`Hashable`, `autoreleasepool`, `ObjCBool`, CF types as `Hashable` (`_CFObject`), CFString round trips, and CGFloat. Build them for `<arch>-apple-macosx26.0` against these overlays, link with Darling's ld64 (plus `-Xfrontend -disable-objc-attr-requires-foundation-module`, since there is no Foundation Swift overlay), and run them with `darling shell`.

`tests/data_sendable.swift` checks that `Data` is `Sendable`; build it with `-swift-version 6`, because language mode 5 only warns.

`tests/data_span.swift` covers `Data.bytes`, `.span`, `.mutableBytes` and `.mutableSpan` for empty, inline, slice and `Int32.max`-byte Data, copy on write, a `Data` made from an `NSMutableData` or from an immutable `NSData` (`Data(referencing:)`, also as a slice whose parent is gone and at `Int32.max` bytes, with a round trip back through `NSData`; a write must not reach the `NSData`) and `bytesNoCopy`.

`tests/data_nsdata_aliasing.swift` checks that a `Data` made from an `NSData` is a value: `withUnsafeMutableBytes`, the subscript, `replaceSubrange`, `append` and `resetBytes` change that `Data` only (also after a round trip through `NSData` and an `NSArray` hop, for a slice whose parent is gone and at `Int32.max` bytes).

## Foundation coverage

The Foundation overlay is intentionally partial. Of the 4452 names the Swift 5.2.2 `libswiftFoundation` exported, 1298 are still exported by macOS 26 and were missing from the first source build. The files taken from `release/5.4` of apple/swift (commit 845205b4407cb1e50ebe69a4d1174714338337c3, `stdlib/public/Darwin/Foundation`) close most of that gap: CocoaError, URLError, POSIXError, MachError (`NSError.swift` split by type), ErrorUserInfoKey, URLResourceValues and the URL bookmark and resource value members (`URL.swift`), NSValue bridging of NSRange and the CoreGraphics types (`NSValue.swift.gyb` expanded with that commit's `utils/gyb.py`), `NSGeometry.swift`, the NSArray, NSSet, NSDictionary, NSIndexSet, NSData, DispatchData, NSExpression and NSSortDescriptor extensions, and the NSString-backed String and StringProtocol members (adapted, see `NSStringAPI.swift`). Each file keeps Apple's header and a note on what was adapted for Darling's headers. `URLComponents.rangeOfX` is written for Darling's Swift-implemented URLComponents.

The Combine integration is now built (`Schedulers+RunLoop`, `Schedulers+OperationQueue`, `Publishers+Timer`, `+NotificationCenter`, `+URLSession`, `+KeyValueObserving`, `CombineTypealiases` from the same `release/5.4` commit; `Schedulers+Date.swift` is reduced to the `Stride` typealias because `Date.swift` already declares the members) together with the `TopLevelEncoder`/`TopLevelDecoder` conformances of the JSON and property-list coders; `tests/combine.swift`, `combine_merge.swift`, `combine_combine_latest.swift`, `tests/foundation_publishers.swift` and `tests/kvo_publisher.swift` cover them. `Measurement` (`Measurement.swift`, same `release/5.4` commit, `tests/measurement.swift`) needs Foundation's API notes to import NSUnit, NSDimension, NSUnitConverter, NSUnitConverterLinear and the NSUnit<Dimension> classes as Unit, Dimension, UnitConverter, UnitConverterLinear and Unit<Dimension>. It does not include `Measurement.FormatStyle` and `formatted()` (swift-foundation only has a stub of them outside Apple's own build), `Locale.MeasurementSystem` or `Dimension.init(forLocale:)`. Still missing, each blocked outside this repository: URLResourceValues properties whose resource keys or types are not in Darling's NSURL header, NSURL promised-item and temporary resource value methods, NSCoder/NSKeyedUnarchiver top-level decode methods, NSProgress refined properties, Calendar weekend searches, URLComponents/URLQueryItem bridging, `PlaygroundQuickLook` members. The names that the other still-prebuilt overlays import from libswiftFoundation all resolve (checked with `llvm-nm -m`). The overlay needs the Foundation headers and API notes with the Swift names (NS_OPTIONS/NS_ENUM, bridges, DateFormatter, typed resource keys) in the SDK.

## CryptoKit

`CryptoKit.framework` is the Crypto module of [apple/swift-crypto](https://github.com/apple/swift-crypto) at tag 5.1.2 (commit `3280a5f72874d2f73bf25551bbb64f524c76d834`, Apache-2.0), compiled as the Swift module `CryptoKit` instead of `Crypto`. swift-crypto's README states that its API files are the same as Apple's CryptoKit source; that is the project's claim, and its README also says that it keeps no stable ABI. `overlays/CryptoKit` has the build rules; `DARLING-CHANGES.md` lists every difference from upstream; `NOTICE.md` has the licences.

**Building.** `SWIFT_CRYPTO_SOURCE_DIR` is a checkout of swift-crypto at that tag (by default the sibling directory `../swift-crypto`). The `darlinghq/swift-crypto` mirror that the main repository would pin as a submodule does not exist yet. The tag 5.1.2 and a branch `darling/cryptokit-rename-5.1.2` are in the temporary personal fork `cristim/swift-crypto`, which a maintainer is to move to `darlinghq`; until a mirror is pinned the checkout has to be provided by hand. `DARLING_CRYPTOKIT` is `AUTO` (build when the checkout is there, say so and skip when it is not), `ON` (stop configuring when it is not there) or `OFF`. The framework adds 243 BoringSSL C++ files, 38 assembly files and 5 XKCP C files to the build, next to about 100 Swift files.

**What is compiled.** The lists are in `overlays/CryptoKit/sources.cmake`, generated from the checkout and compared with swift-crypto's own lists (the header of the file says how):

- the 96 Swift files of `Sources/Crypto` (all but the two named below), as the module CryptoKit;
- the 8 files of `Sources/CryptoBoringWrapper`, compiled without library evolution as a module of their own and linked into the framework (they use `package` access, so both modules get swift-crypto's `-package-name com.apple.swift-crypto`);
- BoringSSL (`Sources/CCryptoBoringSSL`): 243 C++ files and the Mach-O assembly for x86_64 and arm64, built with `-std=c++17 -fno-exceptions -fno-rtti -fvisibility=hidden -DNDEBUG` (the assembly files and XKCP's C files without the C++ flags). BoringSSL's symbols are prefixed `CCryptoBoringSSL_` upstream;
- XKCP (`Sources/CXKCP`, `Sources/CXKCPShims`): the Keccak code behind SHA-3.

`unexported.txt` keeps the C symbols (`_CCryptoBoringSSL*`, `_CXKCP*`, `_Keccak*`, `_SHA3_*`, `_SHAKE*`) and the symbols that mention `CryptoBoringWrapper` out of the export table.

The `unexported.txt` pattern `_$s*19CryptoBoringWrapper*` (the module name has 19 letters) keeps the wrapper's own symbols (`$s19CryptoBoringWrapper...`) out of the export table, not every internal symbol that mentions it: in the first successful build nine exported names (llvm-nm) refer to the wrapper module through Swift's word substitution, as `0A13BoringWrapper` or `0D13BoringWrapper` (`Crypto` is the substituted word), so the pattern misses them. They are CryptoKit's own internal symbols, for example the `group` of `P256` and `readRawPublicNumbers`, and harmless. The C patterns are redundant: everything native is built with `-fvisibility=hidden`, and in the built framework all 5975 global symbols of the 286 native objects are private external (hidden), so none reaches the export table. The patterns stay as defence in depth, in case a source is ever compiled without the flag.

**What is rewritten.** `rewrite-sources.cmake` copies the Swift files into the build directory and changes three things; the checkout is never written. A fourth and fifth rule map a failed AEAD open (`AES.GCM.open`, `ChaChaPoly.open`) to `CryptoKitError.authenticationFailure`, as on macOS (see `DARLING-CHANGES.md`, "Failed AEAD open"). Every API file of swift-crypto starts with `#if canImport(CryptoKit)` and re-exports Apple's CryptoKit when it is true, with the implementation in the `#else` branch; the module being compiled is named CryptoKit, so the 92 tests become `#if canImport(CryptoKit) && !DARLING_CRYPTOKIT_MODULE` and the compiler gets `-DDARLING_CRYPTOKIT_MODULE`. Four names qualified with the module name `Crypto.` become `CryptoKit.`. Three initializers that are `@inlinable` become `@usableFromInline`: the framework is built with library evolution, and there an `@inlinable` initializer of a struct that is not `@frozen` may not assign a stored property ("'self' used before 'self.init' call or assignment to 'self'"). They are `init(rawRepresentation:)` of `OpenSSLCurve25519PublicKeyImpl` in `Keys/EC/BoringSSL/Ed25519_boring.swift` and in `X25519Keys_boring.swift`, and `init(wrapping:)` of `OpenSSLNISTCurvePublicKeyImpl` in `NISTCurvesKeys_boring.swift`; each is named by file and exact text and must occur once. The numbers are checked before any file is written, so a different tag stops the build instead of giving an empty or half-rewritten module.

**What is excluded.** `CryptoError_boring.swift` (the typealiases `CryptoError` and `CryptoASN1Error` are not in Apple's documented CryptoKit API); `_CryptoModuleAnchor.swift` (a symbol that only the Apple build of swift-crypto needs); swift-crypto's `CryptoExtras` and `_CryptoExtras` (RSA, OPRF and other APIs that are not CryptoKit); the three BoringSSL socket files that swift-crypto's `Package.swift` excludes; `.gyb` templates, `Docs.docc` and the privacy manifests.

**What is not provided.** `SecureEnclave` (its public signatures use `SecAccessControl` and `LAContext`, and swift-crypto has no implementation: hardware keys cannot be built from these primitives) and `CorecryptoCurveType`. A program that binds either one does not link. If one is needed, an inert shape would have to be written from the public documentation; what it should throw is not documented, so that needs the maintainers' approval first.

**How it differs from macOS.**

- The engine is BoringSSL and XKCP inside the framework. On macOS CryptoKit sits on corecrypto; this is a documented deviation from the layering rule of the main repository's AGENTS.md and needs the maintainers' acceptance. `CryptoKitError.underlyingCoreCryptoError` carries a BoringSSL error value here.
- `Util/BoringSSL/Zeroization_boring.swift` is guarded by `!canImport(Darwin)`, so it is not compiled and key material is cleared with Darling's libc `memset_s`. GUESS: that Darling's `memset_s` is not optimised away.
- Randomness has two sources. Symmetric keys and nonces take it from Swift's `SystemRandomNumberGenerator` (`CryptoBoringWrapper/Util/RandomBytes.swift:23-26`, `Crypto/Util/BoringSSL/RNG_boring.swift:26`; callers in `Crypto/AEADs/Nonces.swift:149` and `:272`, `Crypto/Util/SecureBytes.swift:515`). Asymmetric key generation uses BoringSSL's own generator: `X25519_keypair` (`Keys/EC/BoringSSL/X25519Keys_boring.swift:78`), `ED25519_keypair` (`Ed25519_boring.swift:47`), `EC_KEY_generate_key` (`NISTCurvesKeys_boring.swift:162`), `MLDSA65_generate_key` and `MLDSA87_generate_key` (`Signatures/BoringSSL/MLDSA_boring.swift:106` and `:408`) and `XWING_generate_key` (`KEM/BoringSSL/XWing_boring.swift:145`). Under macOS that generator reads entropy with `getentropy` and detects forks with `pthread_atfork` (`Sources/CCryptoBoringSSL/crypto/rand/internal.h:31-34` and `:43-46`; `fork_detect.cc:166`). UNVERIFIED: that Darling's libsystem provides `getentropy` and `pthread_atfork`. GUESS: that it does.
- Equality of digests, MACs, shared secrets and keys uses swift-crypto's `safeCompare`, a Swift loop, as upstream does. It is not guaranteed constant time by the compiler.

**Verification.** Built and linked: `ninja swiftCryptoKit` for arm64 Debug (jobs=1) builds and links in 5 min 16 s (peak 617 MB; the framework is 5.0 MB), on top of the Foundation changes of the Data PR. Only the arm64 slice was built: the x86_64 slice, with BoringSSL's x86_64 assembly, is UNVERIFIED. Run: `tests/cryptokit_smoke.swift` (SHA-256 and HMAC-SHA-256 against the FIPS 180-4 and RFC 4231 values, built like the other tests) printed PASS, 9 checks, from a hand-overlaid copy of another agent's `master` prefix with the Foundation overlay and CryptoKit.framework copied in. That is verified on a refresh prefix plus overlay, not on a clean install and not on `master`. The install rules were read (`cmake_install.cmake`: `Versions/A` with the `Current` and top-level links, the same rules as Combine.framework) but a full install and a package build were not run. Settled by the build, UNVERIFIED before it: the sources compile with library evolution (after the three `@usableFromInline` changes), `-swift-version 6` takes effect, a library-evolution module may import the non-evolution `CryptoBoringWrapper`, the `.cc` flags override is in effect, and arm64 needs `-Xarch_arm64 -march=armv8-a+crypto` for `__ARM_FEATURE_AES` and `__ARM_FEATURE_SHA2`, so the arm64 slice assumes the AES, PMULL, SHA1 and SHA256 instructions and fails with SIGILL on a CPU without them. No C++ runtime symbol is needed: `llvm-nm -u` of the built framework lists 620 undefined symbols and none is `__Z*`, `___cxa*`, a personality routine or `operator new` (the framework still links `libc++.1.dylib`). The export table has no unwanted names: the reviewer's llvm-nm found none of BoringSSL's or XKCP's, only the nine internal wrapper names above. The names that an application imports from Apple's CryptoKit are not known to this project, so whether the framework's mangled names, protocol requirements, `@frozen` layouts and inlinable helper symbols equal Apple's cannot be checked here: a clean build does not show it, and only the application's undefined-symbol names, with a Mac for layouts, can. The dylib's compatibility version 1.0.0 and current version 0.0.0 are GUESS, not Apple's values.

**Known-answer tests.** Three more tests next to `tests/cryptokit_smoke.swift` check the primitives against the published values, through documented public API only; each is a single-file program that follows the same convention (a `check()` helper, `ok:` and `FAIL:` lines, a final `PASS:` line, exit status 1 on failure):

- `tests/cryptokit_kat_hash.swift`: SHA-1, SHA-384, SHA-512 and SHA3-256 (NIST example values for FIPS 180-4 and FIPS 202), HMAC-SHA-256/384/512 (RFC 4231 section 4.3, test case 2), HKDF-SHA-256 (RFC 5869 appendix A.1) and `SymmetricKey` comparison.
- `tests/cryptokit_kat_aead.swift`: ChaCha20-Poly1305 (RFC 8439 section 2.8.2) and AES-GCM with 128, 192 and 256-bit keys (McGrew and Viega, GCM specification, appendix B, test cases 1-4, 7-8 and 13-16), each with flipped-bit and wrong-key checks.
- `tests/cryptokit_kat_curves.swift`: X25519 (RFC 7748 section 6.1), Ed25519 (RFC 8032 section 7.1, tests 1 and 2), P-256 ECDSA verification (RFC 6979 appendix A.2.5), P-256 ECDH (RFC 5903 section 8.1) and checks that randomly generated keys and nonces differ and work.

The vectors are the standards' test data (no prose is copied) and were each recomputed on the host with openssl, python3 hashlib/hmac or libcrypto. The three files were built and run in a Darling guest, on a hand-overlaid copy of a `master` prefix with the Foundation overlay and CryptoKit.framework copied in (a refresh prefix plus this overlay, not a clean install and not `master`), and each printed its `PASS:` line: 27 `ok:` lines for the hash file, 64 for the AEAD file and 44 for the curves file, 0 `FAIL:`; 27 + 64 + 44 = 135, the count of the single program they were split from, which also passed. They are compiled by hand, not by any in-tree target, and only the arm64 Debug framework was tested. Not covered: SHA3-256 of "abc" (the NIST example files do not give it) and AES-GCM with an IV that is not 96 bits.

## Prebuilt overlays

The Swift runtime and the Swift 5.2.2 overlays that are not built from source yet are the unmodified files of swift.org's `swift-5.2.2-RELEASE-osx.pkg` (and the 6.3.3 runtime pkg); they stay byte-identical in this repository. The overlays name their dependencies as `@rpath/libswift*.dylib` and carry no `LC_RPATH`, and macOS 26 has no `@rpath` fallback, so `prebuilt_install.cmake` installs copies whose load-command paths differ: every `@rpath/libswiftX.dylib` dependency (and an `@rpath` install ID) becomes the absolute `/usr/lib/swift/libswiftX.dylib`. The copies are made in the build directory with the host `install_name_tool` that Darling builds from cctools-port, and are ad-hoc signed by `adhoc-sign` like every other image of the build. Only a reference to `@rpath/XCTest.framework` (a framework that comes with Xcode) is left.
